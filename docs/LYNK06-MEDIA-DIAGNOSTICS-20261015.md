# 原车仪表媒体诊断记录

初始实现日期：2026-10-15。当前状态更新：2026-10-17。诊断对象是原车仪表音乐区域的 CarPlay 播放信息、封面和媒体控制链路。

## 自动记录

### 媒体控制

- 每次 CarPlay 媒体请求分配进程内编号，记录指令、来源、当时播放状态及是否已处于目标状态。
- 同一编号记录排队耗时、HID 按下和释放结果；事件通道缺失与写入异常单独记录。
- 手机播放状态或歌曲信息变化时列出候选请求编号，但不把时间相邻直接当作手机对特定指令的确认。
- 请求五秒后记录观察窗口，区分排队、正在写入、已发送和迟到执行。
- 原车媒体中心回调记录指令、来源、控制权、处理结果，以及当时的仪表地图状态版本。

### 歌曲、进度与封面

- 当前歌曲列表记录 `trackRevision`、单项数量、iPhone 封面引用、图片短编号和发布原因。
- 播放信息记录来源、播放状态、封面有无和原车返回结果。
- 进度更新独立于歌曲与封面发布，避免每秒重发播放信息。
- 封面 HTTP 服务记录登记、GET/HEAD、状态、响应字节、异常和耗时。
- `getArtwork` 记录调用总数、空值总数和空/非空翻转，区分“原车未调用”和“调用时仍无封面”。
- 原车日志订阅保存 `MusicPlaybackInfoHelper`、`ThreeAlbumService` 和 DIM 事件，并执行现有脱敏与限流。

### 地图与物理显示边界

封面和媒体日志附带 `mapRevision`、`appMapReady` 和最后 MCU 指令，用于比较地图开启与媒体现象。

HTTP 200 只表示图片响应已写出；HID 写入成功只表示本地事件已发送；`appMapReady` 只表示应用地图输出就绪。这些结果都不能单独证明物理仪表完成封面渲染或手机执行了指令。

## 自动化覆盖

现有测试覆盖：

- 请求排队、按下/释放失败、多请求候选、延迟执行和关闭。
- GET/HEAD 响应、不同图片关联、读取失败和会话清理。
- 原车日志权限拒绝、脱敏、限流、进程退出和关闭终止。
- 当前歌曲列表字段、封面 Uri、先列表后播放信息及重复信息去重。
- `getMultiMediaList` 空 Parcelable 返回格式。

## 实车记录

### 2026-10-15 单曲对照

原车已从回环 HTTP 解码并保存 CarPlay 封面；同步当前歌曲列表后，仪表广播不再引用原车旧歌曲，用户确认当前歌曲显示正确封面。该结果只覆盖本次歌曲与场景。

### 2026-10-16 综合采集

- 下一曲、上一曲、暂停均收到原车媒体中心回调并操作成功。
- 应用累计记录封面 HTTP `requests=58 served=58 failures=0`。
- 原车播放信息记录 `appName:LynkPlay` 和本应用发布的封面 URL。
- 用户在三次媒体操作后均未看到仪表媒体中心封面。
- 同一轮应用报告中 `clusterMusic=enabled=false` 指的是 LynkPlay 地图上的音乐浮层，不是原车仪表媒体中心，不能用它解释该现象。

两轮结果说明封面链路可以成功，但显示仍不稳定或受场景影响。当前不能把问题只归因于地图开关、图片生成、HTTP 读取或某一个原车组件。

### 0.2.4 协议修正

0.2.4 将 `getMultiMediaList` 的 null 返回改为 Parcelable presence 标记 0，避免原车把 binder 魔数当成 Parcelable 内容解析。该修正已有 Binder 回归覆盖，尚待实车确认对媒体中心稳定性的影响。

## 后续采集

1. 从连接前启动日志采集，保留注册、取得控制权、首次列表和首次封面发布。
2. 固定歌曲和播放源，只切换仪表地图开关。
3. 每次切歌同时记录列表、播放信息、HTTP、原车广播和用户观察。
4. 单独测试长时间播放、快速切歌、前后台、通话后恢复与断开重连。
5. 将“应用发送成功”“原车读取成功”和“物理仪表显示成功”分别记录。
